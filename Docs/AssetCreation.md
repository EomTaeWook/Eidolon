# 다면도 제작

다면도 제작은 기준 이미지 한 장에서 정면·좌측·우측·후면의 4방향 이미지를 만든다. 화면과 MCP의 신규 요청은 GPT(Codex CLI의 기존 이미지 생성 경로)로 고정하며 저장된 공통 지침을 사용한다. 실제 3D 모델을 출력하지 않으며 이미지별 외형과 시점의 정확성은 생성 결과로 확인한다.

## 사용자 흐름

기준 이미지를 고르고 선택적으로 대상 설명을 입력한다. 설명을 비우면 기준 이미지의 같은 대상을 사용한다. 생성 결과의 큰 이미지에서 다면도 제작으로 연결해 원본과 설명을 가져올 수도 있다. 제작 종류·동작·프레임 수·FPS는 입력하지 않는다.

왼쪽 결과 영역에서 기준 이미지를 추가한다. 선택 전에는 추가 버튼, 선택 후에는 기준 이미지, 제작을 접수한 뒤에는 같은 영역에 선택한 결과와 방향별 썸네일·상태를 표시한다. 신규 묶음은 생성·저장·썸네일·시트에 아래 고정 순서를 사용한다. 이전 묶음의 저장 방향 번호와 내보내기 순서는 유지한다. 제작 조건은 오른쪽, 생성·취소와 대기열은 기존 하단에 둔다. 완료 묶음을 고르는 드롭다운이나 자동 최신 선택은 제공하지 않는다.

| 순서 | 라벨 | 방향 |
|---|---|---|
| 1 | `front` | 정면, 대상 바로 앞 |
| 2 | `left` | 좌측, 대상 자신의 왼쪽에서 바라본 90도 측면 |
| 3 | `right` | 우측, 대상 자신의 오른쪽에서 바라본 90도 측면 |
| 4 | `back` | 후면, 대상 바로 뒤의 180도 방향 |


`AssetFramePromptBuilder`는 필요한 카메라 방향을 프롬프트 맨 앞에 놓는다. 같은 자세·형태·색상·장비 부착 위치를 유지하고 카메라만 이동하도록 요청한다. 좌우는 거울상 복사가 아니라 각 면의 특징과 가림 관계를 반영한다.

기존 5방향 묶음과 윗면 파일은 보존하며 이전 묶음의 조회·이어 만들기·내보내기는 기존 저장 조건을 따른다.

각 이미지를 선택해 비교하고 설명 수정 후 선택 재생성 또는 원본을 보존하는 이미지 교체를 할 수 있다. 미완성 이어 만들기는 완료 항목을 유지한다. 재생·FPS·항목 순서 변경은 제공하지 않는다. 생성·취소·대기열 동작은 입력 패널 하단에 두고 공통 상태 영역에는 상태와 진행만 표시한다.

현재 출력 폴더의 갤러리에 표시되는 이미지가 없는 기존 묶음은 제작 화면의 접힌 이어 만들기에서 이름·상태를 보고 명시적으로 연다. 열기만으로 실행하지 않으며, 누락된 방향의 이어 만들기는 기존 실행 버튼으로 요청한다. 목록에 표시할 기록이 없으면 접기 영역도 표시하지 않는다.

배경 투명화·픽셀 아트·출력 크기·열 수는 출력 설정에서 선택한다. 기본 출력 크기는 1024×1024이며 16~2048 px다. 새 시트는 기본 5열이며 UI에서는 1~5열, MCP에서는 1~32열을 받되 실제 이미지 수를 넘는 열은 만들지 않는다. 참고 이미지는 기존 32 MiB·4천만 픽셀 제한을 따른다. 출력 크기는 내보내기 크기이며 모델의 생성 해상도를 바꾸지 않는다.

제작 화면 상단에는 GPT만 표시하며 신규 체크포인트·LoRA·참고 강도·시드 선택은 제공하지 않는다. 접수 시 설정 사본의 생성 방식만 Codex로 고정하고 기존 Codex 실행 모델·경로와 공통 지침을 사용한다. 전역 생성 방식이나 엔진 설정을 변경하지 않으며, 일반 이미지 생성·편집과 3D 모델링의 선택은 유지한다.

## 실행과 저장

기존 `StudioWorkPresenter → StudioWorkQueue → StudioService.GenerateAsync`를 사용하며 묶음 하나가 FIFO 요청 하나다. 새 묶음의 네 이미지는 순서대로 생성하며 설정·공통 지침·참고 이미지는 접수 시 고정한다. 이미 접수됐거나 저장된 ComfyUI 묶음의 실행과 이어 만들기·선택 재생성은 저장된 생성 방식·모델·LoRA·참고 강도·시드와 기존 시드 선택 계약을 사용한다. 저장된 변환 문장은 같은 프롬프트로 재생성하거나 이어 만들 때 재사용한다.

`AssetCreationService`가 묶음 준비·생성·재생성·교체를 소유한다. `JobStore`는 `Jobs/<묶음 ID>/AssetCollection.json`과 `Reference.bin`을 보존하고 각 항목을 원본 Job·출력 PNG·생성 조건 JSON에 연결한다. 별도 큐·저장소·인덱스를 만들지 않는다.

새 묶음은 `FiveViews` 종류로 저장하며 5항목을 검증한다. 기존 `FourViews`는 4항목, `CharacterViews`·`ObjectViews`는 3항목과 저장된 라벨을 유지한다. 과거 스프라이트 기록·이미지는 디스크에서 삭제하지 않으며 현재 제작 목록과 작업 대상에서는 제외한다. 기존 종류의 숫자 값은 변경하지 않는다.

일부 실패와 취소는 완성한 이미지와 기록을 유지한다. 이어 만들기는 완료 항목을 건너뛰고 누락 이미지만 다시 만든다. 선택 재생성이 실패해도 이전 이미지·원본 Job·실제 시드는 유지한다. 비정상 종료한 준비·실행 묶음은 다음 시작에서 중단 상태로 표시하고 자동 재개하지 않는다. Codex의 기존 DTO 시드 값 0은 실제 시드를 뜻하지 않는다.

묶음 삭제는 확인 후 기존 유지 관리 경로에서 큐가 비었을 때만 수행한다. 미리보기 읽기를 종료하고 비트맵을 해제한 다음 `JobStore.DeleteAssetCollection`이 확인된 GUID 작업 폴더를 삭제한다. 출력 PNG·프롬프트 JSON·원본 생성 Job·내보낸 파일은 보존한다. 관리 루트·파일 소유권·링크 검사는 기존 경계를 따른다.

## 생성 결과의 묶음 표시

생성 결과에서 전체·일반 이미지·다면도 필터를 제공하고 다면도는 하나의 묶음 카드로 표시한다. 묶음 안에서는 방향별 최신 이미지를 선택하며 저장·재사용·편집·학습은 선택한 이미지 한 장에 적용한다. 부분 완료 묶음도 현재 출력 폴더에 실제로 있는 이미지를 표시한다. 묶음 카드를 선택 삭제 대상으로 확장하지 않는다.

갤러리의 카드나 방향별 썸네일을 선택하면 갤러리 미리보기만 바뀐다. 선택한 방향의 묶음 ID로 JobStore의 실제 제작 기록을 읽을 수 있을 때만 우측 상세에 제작 화면에서 열기 버튼을 표시한다. 이 버튼은 해당 묶음과 방향을 제작 화면에서 연다. 출력 PNG와 JSON만 가져와 묶음 카드가 표시되는 경우에도 대응 제작 기록이 없으면 열기 버튼을 표시하지 않는다.

기존 `JobStore`가 생성·재생성 후 PNG 옆 `GenerationMetadata`에 `AssetCollectionId`·`AssetFrameNumber`·`AssetFrameLabel`을 기록한다. 이 값은 기존 묶음 ID와 항목 번호·라벨이며 별도 ID·저장소를 만들지 않는다. PNG와 JSON을 함께 옮기면 Job 폴더 없이도 그룹을 표시할 수 있다. 기존 기록은 현재 출력 폴더에서 소유가 확인되는 이미지의 소속만 보충하며 원본 PNG와 기존 생성 조건은 유지한다.

## 내보내기

모든 항목에 이미지가 있어야 한다. 출력 폴더 아래 새 `Eidolon-Assets-<ID 일부>-<새 GUID>` 폴더를 만들고 기존 파일을 덮어쓰지 않는다.

| 파일 | 내용 |
|---|---|
| `Frames/001.png` 등 | 공통 크기로 정렬한 개별 PNG |
| `Sources/001.png` 등 | 선택한 결과의 원본 사본 |
| `Sources/001.json` 등 | 원본 옆에 생성 조건 JSON이 있을 때 그 사본 |
| `Sheet.png` | 저장된 방향 순서로 합성한 투명 시트 |
| `Sheet.json` | 종류·크기·순서·방향 라벨·시트 좌표·기준점·원본 Job·시드 |

미리보기는 원본을 표시한다. 내보내기는 알파 16 초과 영역을 경계로 측정하고 원본 캔버스의 긴 변에 대한 공통 배율로 각 이미지를 정규화해 하단 중앙에 놓는다. 픽셀 아트는 nearest 보간을 사용한다. 이 처리는 대상의 해부학적 기준점을 추적하거나 생성된 형태 차이를 복원하지 않는다.

시트 형식은 `Eidolon.AssetSheet`, 스키마 1을 유지한다. 좌표는 시트 좌상단 원점의 픽셀이며 기준점은 셀 안의 0.5/1.0이다. 새 다면도는 반복 재생하지 않는다. 시트는 왼쪽에서 오른쪽, 위에서 아래로 채우고 최대 면적은 6천4백만 픽셀이다. 실패·취소 시 작성된 사본 일부가 남을 수 있으며 재시도는 새 폴더를 만든다.

ComfyUI 배경 투명화는 기존 배경 제거 서비스를 사용하고 Codex는 내장 이미지 생성의 실제 알파 출력을 요청한다. 내보내기는 원본 배경을 임의 제거하지 않는다.

## 책임과 품질

Core의 기존 요청·묶음 모델, `AssetCreationService`, `AssetFramePromptBuilder`, `JobStore`, 이미지 가져오기·시트 내보내기를 사용한다. App의 제작·미리보기 ViewModel은 입력·선택·명령과 비트맵 수명을 소유하며 `AssetImageLoader`는 제한된 크기로 미리보기를 읽는다. MCP는 같은 경로를 연결하며 도구 계약은 [MCP 연결](Mcp.md)이 소유한다.

방향별 각도·좌우 비대칭·외형 유지·가림 관계를 실제 이미지로 판단한다. 프롬프트나 파일 개수·빌드 성공만으로 정확성 통과를 보고하지 않는다. 원본에서 보이지 않는 면의 세부 형태는 단일 이미지로 확정할 수 없다. 실제 생성 비교와 판정은 [에셋 제작 품질 검증](AssetCreationQuality.md)에 기록한다.
