# 책임 경계 정적 검수

검수일: 2026-10-07. 대상은 저장소의 수작업 C# 105개 파일과 App XAML이다. `bin`·`obj`, `DataContainer/Generated`, 외부 변환 도구는 제외한다. 빌드·테스트·앱 실행은 수행하지 않았다.

## 발견 및 처리

| 발견 | 처리 |
|---|---|
| `StudioViewModel`에 생성·편집·갤러리·학습·자산·엔진·설정 책임이 집중됨 | 기능별 ViewModel로 상태·명령을 옮기고 View의 DataContext·컴파일 바인딩·갤러리 코드 비하인드도 해당 소유자에 연결 |
| 학습 전 엔진 정지는 Core, 학습 후 복구는 화면의 `finally`에 나뉨 | `StudioService.TrainAsync`에서 정지·학습·등록·복구를 처리하고 화면에서 프로세스 제어 의존성을 제거 |
| `JobStore.JobHeader` 내부 클래스와 Windows 프로세스 소유 객체의 내부 구조체 | 각각 기존 계층의 `Models/Jobs`·`Models/Processes`로 분리 |
| 실행·화면 데이터 모델이 서비스·ViewModel 폴더의 최상위에 섞임 | 소유 계층의 `Models` 아래에서 기능별 폴더로 정리. 기존 네임스페이스·직렬화·저장 위치는 유지 |
| 생성 결과 선택의 미리보기 갱신 조건에서 편집 탭이 빠짐 | 생성·편집 공용 작업 공간 조건을 사용하도록 수정 |

## 책임과 수명 확인

- 기능별 ViewModel은 루트 ViewModel을 참조하지 않는다. 공용 상태는 `StudioSession`, 탐색은 `StudioNavigationViewModel`, 기능 간 재사용은 명시적인 생성·학습 메서드와 생성 결과 알림으로 연결한다.
- `SettingsStore`·`AssetLibrary`·`JobStore`의 설정·자산·작업 저장 소유권과 앱 공용 `StudioWorkQueue`·`StudioWorkPresenter`는 유지한다. 같은 데이터의 저장소·캐시·인덱스를 추가하지 않았다.
- 행위가 큰 `ComfyEngine`·`AssetLibrary`·`JobStore`·`LoraTrainer`도 메서드와 의존성을 검토했다. 각각 엔진 연결·프로토콜, 자산 저장, 작업·결과 파일, 학습 실행·데이터셋 준비의 기존 경계다. 파일 길이만을 기준으로 저장 소유자나 실행 흐름을 분할하지 않았다.
- 학습 요청 취소는 학습 프로세스에 전달하고 엔진 복구에는 앱 수명 토큰을 사용한다. 앱 종료 시 복구하지 않는다. 복구 실패는 표시 오류로 전달하고 성공한 LoRA 등록 또는 원래 학습 실패를 변경하지 않는다. 복구 중에도 GPU 사용권을 유지하며 모든 종료 경로에서 반환한다.
- 창 종료는 앱 수명 취소·갤러리 읽기와 큐 종료 대기·알림 구독 해제·비트맵 해제·엔진 종료·토큰 해제 순서다. 닫기 시작 후 갤러리 요청을 추가하지 않는다.
- 언어 변경은 루트에서 각 기능의 표시 항목·파생 문구를 갱신하고 설정 저장은 생성 지침 읽기 전용 표시를 갱신한다. 모델 변경 시 호환 LoRA와 이어 학습 선택의 재연결을 유지한다.

## 정적 확인 결과

- C# 구문 트리를 읽어 구문 오류와 내부 타입이 없음을 확인했다. 비모델 최상위 타입은 파일별로 분리되어 있고, 함께 배치한 Windows API 구조체는 `Models` 안의 같은 데이터 계약이다.
- 분리 전 루트 멤버와 분리 후 기능별 멤버의 참조를 대조했다. 기능 사이에 빠진 메서드·필드 참조는 발견되지 않았다.
- XAML을 XML로 읽고 DataTemplate의 항목 타입·상속 멤버를 포함해 바인딩 경로를 소유 타입과 대조했다. 분리 중 잘못 연결된 설치 버튼과 모듈 상태 항목 바인딩을 수정했다.
- Core의 App·Avalonia·언어·테마·번역 서비스 및 UI 문자열 키 참조를 검색해 발견되지 않음을 확인했다.

이 검수는 소스 구조·구문·참조·수명 경로의 확인이다. Avalonia 컴파일 바인딩의 실제 컴파일, UI 표시, ComfyUI 생성·학습·취소의 실행 결과는 검증하지 않았다.
